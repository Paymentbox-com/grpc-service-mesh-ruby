# Generated Code

Generated code is what an application uses this library through. It holds the
`Targets`, the `RPCService` and `RPCClient` classes, and the per-transport
`ServiceMaps` for a set of definitions. The generator writes it into the
definitions project, and it is not edited by hand.

The specification is the reference for everything about generating it:

- [Generator](https://github.com/Paymentbox-com/grpc-service-mesh-api/blob/master/docs/generator.md) covers installing and running
  `grpc-service-mesh-gen`, its flags, and the files it writes.
- [Generated Code](https://github.com/Paymentbox-com/grpc-service-mesh-api/blob/master/docs/generated-code.md) covers what is generated for each
  service and how the types and `ServiceMaps` are named.

This page shows the Ruby output for this library's reference definitions, and
lists the parts of this library that generated code relies on.

## Reference Output

The reference definitions are in `spec/support/definitions/`, laid out as a
definitions project. `shop/order.proto` declares `shop.OrderService`, and
`shop/deployment.proto` sets the directory's transport to `mem`, the in-memory
transport the specs use. `just proto-test` runs `grpc-service-mesh-gen` at the
version `gen_version` names in the `justfile`, the same way a consumer runs it,
and writes the output to `spec/support/testproto/`:

```
spec/support/testproto/shop/order_pb.rb        message code
spec/support/testproto/shop/deployment_pb.rb   message code
spec/support/testproto/shop/shop_grpcmesh.rb   Shop::OrderTargets, Shop::OrderService, Shop::OrderClient
spec/support/testproto/service_maps.rb         one ServiceMap per transport
```

CI regenerates the output and fails when it differs from what is committed, so
the reference always matches the pinned generator. The specs run against it.

`shop/shop_grpcmesh.rb`:

```ruby
# frozen_string_literal: true

# Generated by grpc-service-mesh-gen. DO NOT EDIT.
# source: shop/order.proto
# transport: mem
# deployment group: shop

require "grpc_service_mesh"
require "google/protobuf/empty_pb"
require_relative "order_pb"

module Shop
  module OrderTargets
    PLACE = ServiceMesh::Target.new(
      segments: ["shop", "OrderService", "Place"],
      kind: :route,
      metadata: {"deployment_group" => "shop", "transport" => "mem"}
    )
    PLACED = ServiceMesh::Target.new(
      segments: ["shop", "OrderService", "Placed"],
      kind: :topic,
      metadata: {"deployment_group" => "shop", "transport" => "mem", "consumer_group" => "audit"}
    )
  end

  class OrderService < GrpcServiceMesh::RPCService
    rpc :place, target: OrderTargets::PLACE, input: Shop::Order, output: Shop::Order, kind: :route
    rpc :placed, target: OrderTargets::PLACED, input: Shop::Order, kind: :topic
  end

  class OrderClient < GrpcServiceMesh::RPCClient
    rpc :place, target: OrderTargets::PLACE, input: Shop::Order, output: Shop::Order, kind: :route
    rpc :placed, target: OrderTargets::PLACED, input: Shop::Order, kind: :topic
  end
end

::Google::Protobuf::Empty.include(GrpcServiceMesh::Metadata)
::Shop::Order.include(GrpcServiceMesh::Metadata)
```

`service_maps.rb`:

```ruby
# frozen_string_literal: true

# Generated by grpc-service-mesh-gen. DO NOT EDIT.
# One ServiceMap per transport, holding every Target served over it.

require "service_mesh"
require_relative "shop/shop_grpcmesh"

module ServiceMaps
  MEM = ServiceMesh::ServiceMap.new(targets: [
    Shop::OrderTargets::PLACE,
    Shop::OrderTargets::PLACED
  ])
end
```

## What Generated Code Relies On

The generated code calls a class-level declaration on `RPCService` and
`RPCClient`, and includes a module into message classes. These are an
implementation detail between the generator and this library. Applications do
not call them. They are listed here so it is clear what the generator relies
on.

`RPCService` and `RPCClient` share one class-level declaration.

```ruby
rpc name, target:, input:, kind:, output: nil
```

| Argument | Value |
|---|---|
| `name` | The rpc method name in snake_case, as a Symbol. It is the name of the handler method on a service subclass and of the class method on the client. |
| `target:` | The `ServiceMesh::Target` constant for the rpc method. |
| `input:` | The input message class protoc generated. |
| `output:` | The output message class protoc generated. It is required for `:route` and not used for `:topic`. |
| `kind:` | `:route` or `:topic`, matching `target.kind`. |

A `kind:` that does not match the target's kind raises
`ServiceMesh::KindMismatch` when the file loads. `.rpcs` returns every declared
rpc method by name, including those declared on superclasses, as
`GrpcServiceMesh::Rpc` values.

On an `RPCService` subclass, the declaration records the rpc method.
`#endpoints` and `#subscribers` build a `ServiceMesh::Endpoint` or
`ServiceMesh::Subscriber` for each `ROUTE` or `TOPIC` rpc method the
application's subclass defines a method for, as described under
[Handlers](handlers.md). `GrpcServiceMesh.register` reads them.

On an `RPCClient` subclass, the declaration defines the class method
`name(request)`, which calls the transport client's `request` or `publish`, as
described under [Calling](calling.md).

After the service classes, the generated file includes
`GrpcServiceMesh::Metadata` into every message class that an rpc method in the
file takes or returns, which gives those classes `mesh_metadata`, as described
under [Message Metadata](handlers.md#message-metadata).
